CloudCast Scope User Manual

CloudCast Scope is a signal monitor and analyser for NDI®. It connects to a source on the network and measures it the way a rack of broadcast test gear would: picture, waveform, RGB parade, vectorscope, luma histogram, per-channel audio metering, EBU R128 loudness, stream timing, and SCTE-104 cue decoding.

It also does one thing a rack of test gear cannot. It can record the arrival time of every frame to a file and replay that file offline through a downstream pacer's rules, which is how you tell the difference between a source that is losing frames and a source that is delivering them in bursts. Those two faults look identical on a dropped-frame counter and completely different downstream. That is §8, and it is the reason this tool exists.

One native binary, and no service to install. The same analysis runs from the GUI, from a headless --probe over SSH, and offline from --analyse — and, when you turn it on, from a browser on your network (§11).

1. What CloudCast Scope is

A confidence and fault-finding monitor for NDI sources. Point it at a source and it tells you, continuously and numerically:

  • whether the picture is legal (levels, gamut), present (black, freeze) and sharp;
  • whether the audio is present, in phase, clipping, and at what loudness;
  • whether the frames are arriving at the rate and the spacing the sender claims;
  • whether any SCTE-104 cues are riding in the metadata, and what they say.

Everything it measures, it measures from the full-resolution frame. The picture on screen is downscaled for cheap texture upload; no measurement is ever taken from that downscale.

The same analysis is reachable three ways:

Mode Command Use
GUI cloudcast-scope Sit and watch. Scopes, meters, alarms — and timed measurement runs that analyse themselves (§8).
Headless probe cloudcast-scope --probe "Camera 1" --seconds 30 Scripts, cron, SSH. Prints the same numbers and exits.
Offline cloudcast-scope --analyse capture.jsonl Read back a recording made earlier (§8).

Requirements

  • The NDI Runtime, version 5 or 6. This is not the NDI SDK. CloudCast Scope contains no SDK code; it loads the runtime library at process start. The runtime ships with NDI Tools and with most NDI-aware applications, so a machine that already runs NDI Studio Monitor, a switcher or an encoder almost certainly has it.
  • Windows x64 for the supplied MSI. The code itself is portable; the installer is not.
  • Nothing else. No .NET, no browser, no service account, no firewall rule — Scope only makes outbound NDI connections and receives on the ephemeral ports the NDI runtime's own discovery already accounts for.

Without the runtime the application will not start: it exits with NDI runtime not found. Install the NDI Runtime or NDI Tools. Tried: … followed by every path it looked in.

Where the runtime is found

At start-up, in this order, until one loads:

  1. %NDI_RUNTIME_DIR_V6%\Processing.NDI.Lib.x64.dll
  2. %NDI_RUNTIME_DIR_V5%\…, then %NDI_RUNTIME_DIR_V4%\…
  3. C:\Program Files\NDI\NDI 6 Tools\Runtime\…
  4. C:\Program Files\NDI\NDI 6 Runtime\v6\…
  5. C:\Program Files\NDI\NDI 5 Tools\Runtime\…
  6. C:\Program Files\NDI\NDI 5 Runtime\v5\…
  7. Processing.NDI.Lib.x64.dll on the default search path (next to the executable, then PATH).

The environment variables are checked first deliberately: the NDI Tools installer drops the DLL in its own directory and advertises it through NDI_RUNTIME_DIR_V* but does not add that directory to PATH, so probing by library name alone misses it.

2. Installing

The MSI

CloudCastScope-<version>.msi is a per-machine, Authenticode-signed installer. It installs:

  • cloudcast-scope.exe into C:\Program Files\Cloudcast Systems\CloudCast Scope;
  • License.rtf beside it, so the licence travels with the install;
  • a Start Menu shortcut named CloudCast Scope, flat in the root rather than inside a one-item folder;
  • optionally a desktop shortcut — off by default, see below.

There is no service, no scheduled task and no firewall exception. The install directory is changeable on the Destination Folder page of the standard installer UI.

Unattended installs

msiexec /i CloudCastScope-0.1.0.msi /qn
msiexec /i CloudCastScope-0.1.0.msi INSTALLDESKTOPSHORTCUT=1 /qn

INSTALLDESKTOPSHORTCUT=1 is the only property worth setting. It is off by default because a per-machine install writes to the All Users desktop, and imaging a fleet should not silently litter every profile. The choice is remembered in HKLM\SOFTWARE\Cloudcast Systems\CloudCast Scope and honoured on later upgrades — MSI properties do not survive a major upgrade, so without that breadcrumb every upgrade would quietly drop a shortcut somebody had asked for.

The NDI runtime warning

The installer looks for the NDI Runtime but never blocks on it. Staging boxes are routinely imaged with applications first and NDI Tools afterwards, and an operator who hits a hard launch condition has no way to proceed. So the installer detects, records and warns, and succeeds either way.

Two independent signals are checked, because NDI's own installers have moved the runtime around across versions:

  1. The machine-wide NDI_RUNTIME_DIR_V6 / NDI_RUNTIME_DIR_V5 values, read out of the registry hive that backs the machine environment block rather than by expanding %VAR% — the installer process inherited its environment before the NDI installer ever ran, so an expansion would go stale on a same-session install.
  2. The two well-known directories under the native Program Files: NDI\NDI 6 Runtime\v6 and NDI\NDI 6 Tools\Runtime.

If neither is found, the final page of an attended install carries:

Note: the NDI Runtime was not detected on this machine. CloudCast Scope is installed, but it will not start until the NDI Runtime (version 5 or 6) is installed. Get it from ndi.video/tools, then run CloudCast Scope again.

A silent install has no UI to warn into, so the result is recorded as the property NDIRUNTIMEFOUND. To see it, log the install:

msiexec /i CloudCastScope-0.1.0.msi /qn /l*v scope-install.log

and search the log for NDIRUNTIMEFOUND. Its absence means the check found nothing.

Upgrading and uninstalling

Installing a newer MSI replaces the existing install in place. Installing an older one over a newer one is refused with a message telling you to uninstall first — this is deliberate, not a bug. Uninstall from Settings → Apps, or msiexec /x CloudCastScope-0.1.0.msi /qn.

3. The window pane by pane

Four regions: a title bar across the top, the source list down the left, the picture in the centre, and the analysis tabs down the right. The left and right panels are draggable.

Title bar

Left to right:

  • Connection dot — dark grey when nothing is selected; amber when a source is selected but no sender is currently connected; green once at least one connection is up.
  • Source name, exactly as NDI advertises it, e.g. DESKTOP-7HGO8C6 (Airlock Test Pattern).
  • Format line, once video has arrived: 960x540p 25.000 · UYVY · BT.601 · 48000 Hz 2 ch — raster, p/i, frame rate to three decimals, the pixel FourCC actually delivered, the assumed colour matrix (§5), then the audio sample rate and channel count.
  • Alarm chips, right-aligned — see below.
  • Measure, with a duration dropdown beside it — 10 s, 30 s (the default), 1 min, 5 min, 15 min or Continuous. Pressing it starts a timed measurement run; the button area then becomes ■ Stop alongside the elapsed and total time (0:12 / 0:30), the frame count so far, and a progress bar. The run ends itself when the time is up, and the result appears in the Report tab (§8).
  • Picture checkbox — hides the centre pane. Analysis continues; only the texture upload stops.
  • Reset stats — zeroes the analysis counters: received frame counts, timecode discontinuities, clip counts, integrated loudness and LRA, the decoded cue list, the freeze reference and the scope textures. It does not disconnect. It also re-baselines the dropped counts: the receiver's own performance counters keep running, but Scope takes a new baseline from them on the next poll and reports the difference, so the displayed figure means dropped since the last reset or reconnect rather than since the receiver was created. A reconnect restarts the receiver's counters from zero, which Scope detects and re-baselines against, so the figure reads 0 rather than going negative.

Source list and filter

Discovery runs continuously in its own thread for the whole session, so the list updates without any action. The number to the right of Sources is the count currently advertised. The filter box is a case-insensitive substring match on the full NDI name — typing dec finds DESKTOP-7HGO8C6 (Decoder).

Click a name to connect. Clicking the already-connected name does nothing. Disconnect tears the receiver down and clears the snapshot.

An empty list shows Discovering… — that is the normal state for the first second or two, and a persistent state means a discovery problem (§11).

Bandwidth

Three radio buttons, and this choice matters more than it looks:

Setting What arrives Analysis validity
Highest (full analysis) The full-resolution feed. Everything is valid. This is the default.
Lowest (proxy) NDI's ~640×360 proxy stream. Video measurements are not of the real feed.
Audio only No video at all. Audio and audio timing only.

Lowest requests a separately-encoded proxy — a different raster, re-encoded, with its own chroma handling. Gamut counts, sharpness, luma statistics and every scope then describe the proxy, not the signal you care about. Worse, the proxy raster is 360 lines, which flips the colour-matrix inference to BT.601 even for an HD source (§5). Measuring a proxy and reporting it as the feed would be worse than not measuring at all, so selecting it puts a standing amber warning under the radio buttons: Proxy — video measurements are not of the real feed.

Bandwidth is fixed when the receiver is created, so changing it reconnects. The scopes and picture clear, and cumulative counters restart.

Picture pane

The decoded frame, letterboxed into the available space — never stretched. A monitor that lies about aspect ratio is worse than no monitor.

The picture is a nearest-neighbour downscale (longest edge 960 px) converted with the display conversion, which includes the usual 255/219 expansion of studio swing to full range. That is correct for a screen and wrong for a legality test, which is why the gamut check in §5 uses a different conversion on the full-resolution frame.

Alarm chips

The chips only appear while connected, and only when something is actually wrong. When nothing is, a single green OK shows instead. Exactly what lights each one:

Chip Colour Lit when
BLACK red The frame's maximum luma is ≤ 20. Not "dark" — no pixel anywhere above code 20.
FROZEN red Mean absolute luma difference against the previous frame is below 0.05, measured on a 128×128 grid. Live video, even a locked-off camera on a static scene, carries enough sensor noise to clear this; a repeated buffer sits at exactly 0.
DROPS red The dropped-frame count is non-zero for video or audio, measured since the last Reset stats or reconnect. Press Reset stats and watch whether it climbs again — a static count is history, a climbing one is happening now.
SILENCE amber Any channel has stayed below −60 dBFS for 2 seconds.
CLIP amber Any channel's cumulative clip count is above zero. Read §6 Clipping before treating this as a fault.
PHASE amber Correlation between channels 1 and 2 is below −0.5.
A/V SYNC amber The audio and video timestamps differ by more than 40 ms in either direction.
GAMUT amber Out-of-gamut pixels exceed 0.1 % of the raster (minimum 64 pixels).

The GAMUT chip is thresholded while the count in the readout table stays exact, and that asymmetry is deliberate: 4:2:2 chroma is shared across pixel pairs, so every hard colour transition produces a handful of genuinely out-of-gamut edge pixels. A clean colour-bar frame measures a few hundred of them. An alarm that fires on those is lit permanently, which is the same as having no alarm.

4. Scopes

All four instruments are 8-bit code-value displays with the same graticule convention: 16 and 235 are the legal rails and are drawn brighter than the other lines; the regions outside them are tinted faintly red.

Trace brightness is logarithmic in density with a floor, so a single-sample trace is still visible next to a bar carrying a hundred thousand samples.

The waveform, parade and vectorscope are fed from a subsampled grid capped at 200 000 samples per frame (at 1080p that is a stride of 4 in both axes, about 130 000 samples — already far denser than a 256-wide scope can resolve). The luma histogram and every number in the readout table are computed over every pixel.

Waveform monitor

Luma against horizontal position. X is the column across the raster, Y is the luma code with 0 at the bottom and 255 at the top. Graticule at 0 / 16 / 128 / 235 / 255.

The header on the right reads min N max N mean N and turns amber whenever the frame contains any sub-black or super-white pixels — so the numeric warning and the visual one appear together.

What to look for:

  • A trace pressed flat against the bottom rail: crushed blacks, or black.
  • A trace flat-topped at 235: clipped whites. Above 235 and it is illegal.
  • A trace that drifts as a whole between frames: unstable pedestal upstream.
  • Sudden vertical structure at one column: a hard edge, a caption or a burn-in.

RGB parade

The same waveform three times — R, G and B side by side, each tinted with its own primary, each with the same 16/235 graticule. This is where a colour cast shows: on a neutral grey ramp the three traces should sit at the same heights. One channel riding higher at the black end is a lift on that channel; one clipping earlier at the top is a gain error.

The bottom-right corner reads RGB PARADE normally and switches to a red ILLEGAL n — the exact out-of-gamut pixel count — whenever that count is above zero.

Vectorscope

Chroma plotted as Cb across against Cr up, on a circular field. The centre is neutral (128, 128) and the outer circle is 128 code values from centre, so the whole 0–255 chroma range is on screen. The dashed lines are the I axis (123° from +Cb) and the Q axis perpendicular to it, and there is a small crosshair at the centre.

The six labelled boxes — R, MG, B, CY, G, YL — are the targets for 75% colour bars encoded to Rec.709, computed from Cb = 128 + 224(B′−Y′)/1.8556 and Cr = 128 + 224(R′−Y′)/1.5748 with each primary at 0.75.

Reading a source that misses them:

  • Dots land in the boxes. A 75% Rec.709 bar signal, correctly encoded. Nothing to do.
  • Dots land short of the boxes, on the right angles. Under-saturated — either genuinely (a camera, a graphic) or because the bars are 75% amplitude through a gain error. The angles are hue; the radii are saturation.
  • Dots land past the boxes. Over-saturated. Check the RGB parade and the illegal-pixel count: over-saturation is the usual cause of a gamut failure.
  • Every dot rotated by the same amount. A hue shift, which is what a chroma phase error looks like.
  • Dots sit on the right hues but consistently off-radius, and the source is SD or a proxy. This is normal and is not a fault: the targets are Rec.709, and a source at 576 lines or fewer is decoded as BT.601 (§5). Its bars land in the right sectors but not in the boxes. The figure above shows exactly this — a 960×540 source, so BT.601, so the trace does not sit on the 709 targets.
  • A single blob at the centre and nothing else. Monochrome — either a genuinely grey picture, or chroma has been lost upstream.

Luma histogram

Occurrences of each of the 256 luma codes across the whole frame, on a logarithmic height scale (a broadcast histogram is unreadable linearly once one code — black, usually — dominates). Bars below 16 and above 235 are drawn red; the rest are green. Ticks at 0 / 16 / 128 / 235 / 255.

This is the fastest way to see quantisation damage: a comb pattern of empty bins between populated ones means the signal has been through a narrow bit depth or a level stretch somewhere upstream.

What correct colour bars look like

For 75% bars — the standard confidence signal — expect all four instruments to agree:

  • Waveform: eight discrete flat plateaus, descending left to right. The white bar sits at 180 (75 % of the 16–235 excursion), the black bar at 16. Nothing above 180, nothing below 16, and the plateaus are flat, not sloped.
  • Parade: the same eight columns in each of R, G and B, each channel either at 180 or at 16 for each bar, giving the familiar descending staircase in R, the two-step pattern in G and the alternating pattern in B.
  • Vectorscope: six tight dots, one per chromatic bar, plus a dot at the centre for the white and black bars. On a Rec.709 HD source they sit inside the target boxes.
  • Histogram: eight spikes and essentially nothing between them.
  • Readouts: Luma min / max = 16 / 180, Sub-black px = 0, Super-white px = 0, Illegal RGB px a few hundred at most (the 4:2:2 edge pixels described in §3), Frame difference small but non-zero if the pattern carries a clock or animation.

Anything else on a bar signal is a fault in the path, not in the bars.

5. Video measurements

The readout table

Under the scopes, on the same tab. Values in red are out of spec.

Field Definition What a bad value looks like
Luma min / max Lowest and highest luma code present anywhere in the frame, from the full 256-bin histogram. For 4:2:2 this is Y straight off the wire; for RGB formats it is computed with the matrix's luma weights. 0 / 255 on a camera feed: full-range content on a studio-range path. 16 / 16: black.
Luma mean Mean luma over every pixel. Drifting steadily between frames: an unstable pedestal or auto-exposure hunting.
Sub-black px Count of pixels with Y < 16. No tolerance — Y is read straight off the wire with no matrix in the path, so there is no rounding to forgive. Any non-zero count on a properly legalised feed. A few thousand on a noisy camera in deep shadow is common and benign; a fifth of the raster is a level error.
Super-white px Count of pixels with Y > 235. Same, no tolerance. Non-zero on graphics or titles usually means full-range assets pasted into a studio-range path.
Illegal RGB px Count of pixels whose derived R′, G′ or B′ falls outside 16…235, ± a 3-code tolerance (below). A few hundred on a clean bar frame is expected. Tens of percent of the raster is either a genuine gamut fault or a matrix mismatch (below).
Frame difference Mean absolute luma delta against the previous frame, over a fixed 128×128 nearest-neighbour grid, on a 0…255 scale. Exactly 0.000 for more than a frame: the picture is frozen. The first frame after connecting, and the first after any resolution change, always reports 0.000 because there is nothing to compare against — that is why the FROZEN chip needs two frames to light.
Sharpness Mean absolute horizontal luma gradient: the average of |Y[x] − Y[x−1]| over every adjacent pair in the frame. A flat field is exactly 0. One-pixel black/white stripes exceed 100. There is no absolute "good" figure — watch it relative to itself: a live feed that drops by half has gone soft (focus, or a soft upscale has appeared in the path).
Letterbox t/b Count of entirely black rows at the top and at the bottom. A row counts as black when its brightest pixel is ≤ 20. Non-zero when you expected full-height content: the source is letterboxed. A wholly black frame reports its whole height as the top border and 0 as the bottom, rather than double-counting the same rows.
Pillarbox l/r The same for entirely black columns at the left and right edges. Non-zero on 16:9 content: 4:3 material in a 16:9 raster.
Aspect ratio The picture aspect ratio the sender declares, to four decimals. 1.7778 for 16:9, 1.3333 for 4:3. A value that disagrees with width/height means non-square pixels — check before blaming a scaler.

Alpha range and transparency are measured too (the analysis library reports alpha_min, alpha_max and a transparency flag for BGRA/RGBA sources), but they are not shown in this table. Formats without a meaningful alpha channel report fully opaque rather than reporting the padding byte.

Colour matrix inference

The title bar shows BT.601 or BT.709. It is displayed because it is an inference, not something the sender told us.

NDI carries no colorimetry flag. There is nowhere in the frame header that says which Y′CbCr matrix the sender encoded with, so the matrix has to be guessed, and the universal convention is by raster height:

Raster height Matrix assumed
≤ 576 lines BT.601 (covers 480i, 576i, and the sub-SD rasters NDI proxies produce)
> 576 lines BT.709

Getting this wrong is not cosmetic. Decoding a 601-encoded frame with the 709 inverse pushes every saturated colour well outside the legal box: in the regression test that pins this behaviour, a clean 960×540 bar signal decoded on the wrong matrix flags more than a quarter of the entire raster as illegal, while the same bytes on the right matrix flag under 1 %. A clean signal reads as massively out of gamut, and the operator goes hunting for a fault that is not there.

So: if you see a large gamut count, check the matrix in the title bar against what you know the source to be before anything else. The two cases that break the convention are a sub-576-line source that is really 709 (a downscaled HD feed), and a proxy stream — which is why Lowest bandwidth invalidates the gamut figure twice over.

Gamut tolerance

The illegal-RGB test allows 3 code values of slack outside 16…235 — i.e. it flags a pixel only when a derived component falls outside 13…238. That tolerance is an error budget, not a fudge.

A colour sitting exactly on a rail — which every saturated colour bar does — cannot survive the round trip through 8-bit 4:2:2 without landing a code either side of it. The chroma pair is quantised to 8 bits, shared between two pixels, and senders commonly truncate rather than round when packing it. A real NDI colour-bar source measured during development encodes Cb as 43.67 and stores 43; that 0.67-code error alone puts B′ on 14.9 where the true value is 16.

With zero tolerance, that wholly legal frame reads as roughly 58 % out of gamut — worse than not measuring at all.

The size comes from the arithmetic. Decoded R′ = Y + k·(C − 128), so the error is εY + k·εC + ε_fixedpoint. A truncating sender contributes up to −1 code on each of Y and C, the fixed-point conversion up to −1 more, and the largest inverse coefficient is 1.73 (BT.601 Cb→B′). Worst case ≈ −3.7; the real source measured reaches −2. Three codes covers observed reality with margin while staying far below a genuine gamut fault, which runs to tens of codes. Real legalisers carry a tolerance for exactly this reason.

The tolerance is deliberately not applied to the sub-black and super-white luma counts, which read Y off the wire with no matrix and no subsampling in the path.

One more thing about the derivation: the conversion used for the gamut test omits the 255/219 (1.164) luma gain that a display conversion carries. With that gain, a perfectly legal Y = 16 black would map to R′G′B′ = 0 and the whole frame would flag. A gamut check wants the un-expanded R′G′B′, where legal video stays inside 16…235 exactly as the luma does.

6. Audio

The Audio tab carries the channel meters, the R128 readouts and LU bar, the correlation meter and the spectrum. Analysis adapts automatically to the sender's channel count and sample rate — including 44.1 kHz and 96 kHz, which NDI senders emit freely.

A figure of the Audio tab is not included in this revision; see the note at the end of §11.

Channel meters

One bar per channel, scaled 0 to −60 dBFS with key graticule lines at 0 and −18. Each bar carries four things:

  • Banded RMS fill — green below −18, amber from −18 to −6, red above −6. RMS is measured over the window since the previous meter update (~50 ms).
  • Sample-peak line — a solid line at the highest absolute sample in that window.
  • Peak-hold tick — a white tick that holds the highest peak for 1.5 s, then falls at 22 dB/s.
  • Clip box — the small box above the bar, latching red for 2.5 s each time the clip count rises.

Under each bar: the channel number, then the peak value in dBFS, or MUTE when the channel is flagged silent (in which case the whole bar dims). The channel number turns amber when that channel's DC offset exceeds ±0.01 — a genuine DC bias, which will eat headroom and thump on any downstream processing.

— in place of a number means the reading is at or below the −120 dBFS meter floor, i.e. digital silence rather than a very quiet signal.

Peak and true peak

Sample peak is the largest absolute sample value seen. It is what the bar meters show.

True peak is the largest value of the reconstructed waveform between the samples, per ITU-R BS.1770-4 Annex 2: 4× oversampling through a 96-tap Blackman-windowed sinc interpolator (24 taps per polyphase branch), each branch normalised to unity DC gain, with the interpolator's delay line carried across frame boundaries so a peak straddling a buffer edge is still seen. The sample peak is folded in afterwards, because the polyphase branches sample the reconstruction at fractional offsets only.

Why it matters: a signal can read −3 dBFS on sample peak and still clip a downstream converter or a lossy encoder, because the analogue waveform between the samples goes higher. The classic case is a sine at fs/4 with a 45° phase offset: every sample lands on ±0.707 (−3.01 dBFS) while the underlying waveform reaches full scale. Scope reads that as ≈ −0.06 dBTP — the 0.06 dB shortfall is the interpolator's residual passband droop at half-Nyquist, well inside BS.1770-4's ±0.4 dB allowance.

True peak is measured for every channel and printed by --probe as true N dBTP. The GUI bar meters show sample peak and RMS.

EBU R128 loudness

Four readouts above the LU bar:

Readout Window Notes
M Momentary — the most recent 400 ms block.
S Short-term — the most recent 3 s.
I Integrated — everything since connect or Reset stats, gated.
LRA Loudness range, EBU Tech 3342 — 95th minus 10th percentile of the gated short-term distribution, in LU. Needs a few seconds of history before it means anything.

Each shows — until enough audio has accumulated to measure it, rather than a misleading number. Colour: within 1 LU of the −23 LUFS target is green, within 3 LU amber, otherwise plain.

The implementation follows BS.1770-4 literally rather than approximating it:

  1. K-weighting — a high shelf (1681.97 Hz, Q 0.7072, +4.00 dB) followed by an RLB high pass (38.14 Hz, Q 0.5003), both biquads, with coefficients derived for the running sample rate rather than copied from the recommendation's 48 kHz table. The same tone reads the same at 44.1, 48 and 96 kHz.
  2. Blocks — 400 ms at 75 % overlap, i.e. a new gating block every 100 ms.
  3. Gating — an absolute gate at −70 LUFS, then a relative gate 10 LU below the mean of everything that survived the absolute gate. LRA uses the same absolute gate with a 20 LU relative gate.
  4. Channel weighting — 1.0 for L/R/C, 1.41 for the surrounds, 0 for the LFE in a 6-channel layout. Channel counts that do not match a standard layout are weighted 1.0 throughout: over-counting an unrecognised layout is far less surprising than silently zeroing a channel.

Block loudnesses accumulate into a fixed histogram of 0.1 LU bins, so a monitor left running for a week uses the same memory as one running for a minute. A −23 dBFS calibration tone on L and R integrates to −23.0 LUFS ±0.1.

The LU bar underneath spans −18 to +9 LU relative to −23 LUFS, with a green tolerance band at ±1 LU. The thick needle is short-term, the thin one momentary. Changing the channel count resets the integrated measurement — the channel weights, and therefore the summed power, change meaning.

Correlation

Phase correlation between channels 1 and 2 only, computed over the same window as the meters and clamped to −1…+1.

Reading Caption Meaning
+1 MONO above +0.98 The two channels are identical. Correct for a mono source fed to both legs; suspicious on programme audio.
+0.3 … +0.98 CORRELATION Normal stereo.
0 … +0.3 amber Very wide, or largely uncorrelated content. Watch it.
below 0 PHASE Out of phase; will partially cancel in a mono downmix.
below −0.2 OUT OF PHASE, red A leg is inverted somewhere.
below −0.5 also lights the PHASE alarm chip

With fewer than two channels the meter reads MONO SOURCE and the value is 0. When both channels are digitally silent the value is reported as 0 rather than NaN — correlation is undefined there, so do not read 0 as "fine".

Clipping

The clip rule is exactly this: a sample counts as a clip when |x| ≥ 1.0. Counts are per channel and cumulative until Reset stats.

This surprises people, so read it twice: a genuine full-scale sine reports clips continuously and forever. A 0 dBFS 1 kHz tone at 48 kHz has 48 samples per period, which puts a sample exactly on each crest and each trough — 2000 samples per second land on exactly ±1.0, so the counter climbs by 2000 every second and the amber CLIP chip stays lit. Nothing is wrong. That is the rule as specified.

The same tone at 0.999 amplitude (−0.009 dBFS) reports zero clips.

So:

  • On line-up tone at full scale, expect a continuously rising clip count. Line up at −18 or −20 dBFS instead and the question does not arise.
  • On programme audio, any clip count at all is real and worth chasing: music and speech do not sit on the rail.
  • Use Reset stats to zero the counter, then watch whether it climbs again. A count that is not moving is history; a count that is moving is happening now.
  • For headroom questions, look at true peak (above) rather than the clip count — inter-sample peaks above 0 dBTP will not register as clips at all.

Silence

A channel is flagged silent once it has stayed below −60 dBFS for 2 seconds continuously. Its meter bar dims, its label reads MUTE, and the amber SILENCE chip lights.

Two seconds is long enough that a normal pause in speech or a musical rest does not trip it, and short enough to catch a lost leg quickly. The timer is counted in samples, not in wall-clock time, so it is unaffected by how often the UI repaints.

Spectrum

Magnitude spectrum of channel 1 only, from a 1024-point real FFT with a periodic Hann window — 512 bins, about 47 Hz per bin at 48 kHz. Normalisation undoes both the two-sided split and the Hann coherent gain, so a full-scale sine on a bin centre reads ≈ 0 dB.

The x axis is logarithmic from 20 Hz to the lower of Nyquist and 22 kHz, with decade lines at 100 Hz, 1 kHz and 10 kHz. The y axis runs 0 to −100 dB. Several FFT bins share a column in the top octaves, so each column plots the maximum of the bins that fall in it — a narrow tone is never averaged away.

Until 1024 samples have accumulated the panel reads SPECTRUM: WAITING FOR AUDIO. Use it to identify hum (a spike at 50/60 Hz and its harmonics), a lost high end (a hard shelf where a codec's bandwidth limit is), or a stuck tone.

7. Timing

Everything on this tab is measured on this machine's monotonic clock as frames arrive, or read from the receiver's own counters. Nothing here depends on the sender's timecode being correct — that is checked separately.

A figure of the Timing tab is not included in this revision; see the note at the end of §11.

Frame rate and jitter

Row Definition Amber Red

Measured and nominal agreeing does not mean the source is well behaved. A source that delivers frames in pairs with a gap after each pair has a perfect mean rate and is unusable downstream. Mean rate answers "how many"; jitter and the plot answer "when".

The jitter plot below the grid draws the rolling window of inter-frame intervals in ms against an amber line at the nominal period. Its y range always includes half and one-and-a-half times nominal, so a perfectly paced stream still shows the tolerance band rather than auto-scaling into noise. A well-clocked source is a nearly flat line on the amber. A bursty one is a square wave alternating between a very short interval and a long one — the shape in §8.

A/V sync

a/v sync is the last audio timestamp minus the last video timestamp, in milliseconds. Positive means audio is ahead of video. Amber past ±20 ms, red past ±40 ms, which also lights the A/V SYNC chip.

This uses the NDI timestamp, not the timecode. The timestamp is filled in by the receiver's own clock synchronisation and is directly comparable between the video and audio streams of the same source, which is exactly what makes A/V sync measurable. If either stream supplies no timestamp the figure reads +0.0 ms — so a flat zero on a source you know to be out of sync means "not supplied", not "perfect".

Timecode

Both NDI timecode and timestamp are signed 64-bit counts of 100-nanosecond intervals. One second is 10 000 000 units, one millisecond is 10 000.

Two separate rows, and the separation is the point:

  • Video timecode / Audio timecode — present or absent. A value of i64::MAX, i64::MIN or 0 counts as absent. Zero is included because NDI timecodes are referenced to the Unix epoch, so 0 means 1970 — in practice it is what a sender leaves behind when it never assigns the field at all.
  • tc discontinuities — the count of timecode steps that missed the expected one-frame step by more than half a frame, video and audio combined. That catches a dropped frame, a repeated timecode and a jump backwards, while tolerating the rounding a sender does on fractional rates like 30000/1001. For audio, the expected step is samples ÷ sample_rate seconds, since an audio "frame" is however many samples the sender chose to bundle.

A discontinuity count of 0 against an absent timecode is not a clean result — it means nothing is being checked. That is why presence is reported separately instead of being folded into the count. Treating a stuck-at-zero timecode as a real reading would make every frame look like a break and bury the actual finding ("this source supplies no timecode") under a huge fault count.

Dropped frames

The dropped row reads, literally:

dropped: 0 video, 1214 audio

Read the units. The panel names them inline for one reason: an earlier version rendered this as 0 / 1214 against a dropped v/a heading and an operator read it as "0 of 1214" — zero drops out of 1214 frames, i.e. good news. It is the opposite: zero video frames dropped, and one thousand two hundred and fourteen audio frames dropped. Two independent counters, not a ratio. That misreading is what prompted the label change; frames v/a became frames: and dropped v/a became dropped:, each value spelled out with its own unit.

The counts are derived from the NDI receiver's own performance counters, which run cumulatively for the life of the receiver — but what is displayed is the figure measured from the last Reset stats or reconnect, not the receiver's lifetime total. Scope captures a baseline from the receiver on the first poll after a reset and reports the difference from there. A reconnect creates a fresh receiver whose counters restart at zero; that is detected and re-baselined against, so the figure reads 0 rather than underflowing into a huge number.

Either count being non-zero lights the red DROPS chip. Press Reset stats and watch: a count that stays at zero afterwards is history, a count that climbs again is a fault happening now. The frames row above resets on exactly the same event.

A large audio figure alongside zero video is the common pattern, and it usually says something about this monitor rather than about the source: capture and analysis run on one thread, video analysis is by far the more expensive half (about 5 ms per 1080p UYVY frame, more at 2160p), and audio frames are small and frequent, so audio is what the receiver discards when the thread is behind. See §11.

Queue depth connections and bitrate

  • bitrate — video payload bytes over the last second, in Mbit/s, averaged over the real span of the window rather than a hard 1 s divisor (so it does not under-report during the first second). Audio does not contribute.
  • frames — frames: 12 video, 34 audio, received since connect or reset. Same units warning as dropped: two counts, not a ratio.
  • Connections — how many senders are currently connected to this receiver. Zero while a source is selected is why the title-bar dot goes amber. A count of 1 is not proof that frames are arriving — see §11.
  • Queued video / Queued audio — the receiver's queue depth right now, shown in red past 8. A queue that keeps growing means this monitor is not draining frames as fast as they arrive; a persistently deep queue and a rising audio drop count are the same story told twice.

8. Recording and offline analysis

A dropped-frame counter answers "did every frame get here?". It cannot answer "did it get here when it should have?" — and downstream equipment that paces off arrival cares about the second question far more than the first.

A source can deliver every frame, drop nothing, hold a perfect average frame rate, and still be unusable, because it delivers frames in bursts: several close together, then a gap. Anything that emits on a schedule — an output pacer, a genlocked emitter, a delay line — sees that as constant phase error even though nothing was lost.

Recording makes that visible, and --analyse makes it testable offline against a specific downstream pacer's rules.

What a recording contains

JSON Lines: one self-contained JSON object per line, one line per frame. No pixels and no audio samples — just metadata — so an hour of 1080p50 costs a few tens of megabytes and the file loads straight into a spreadsheet, pandas, or --analyse.

The field that earns the format its keep is t_us: the arrival time of the frame, from a monotonic clock, in microseconds since the recording started. It is taken before the preview downscale, so it is as close as possible to when the frame actually arrived rather than including the monitor's own work. Wall-clock time is recorded exactly once, in the session header — as started_unix (epoch seconds) and started_utc (ISO-8601) together — purely so a recording can be correlated with logs from other systems: wall clock can step backwards mid-recording and would make nonsense of interval arithmetic.

started_utc was added after the first release, and the schema version stays 1: it is an added field, and the reader ignores fields it does not know about, so nothing that could read a v1 recording stops being able to. Older v1 recordings, written before the field existed, still load — they simply carry no date on the recorded line of the report.

Record type Fields
session version, started_unix, started_utc, source, tool — written once, first line. started_unix is epoch seconds; started_utc is the same instant as ISO-8601 YYYY-MM-DDTHH:MM:SSZ.
video t_us, tc, ts, w, h, fps_n, fps_d, bytes, luma_min, luma_max, luma_mean, illegal, black, frozen.
audio t_us, tc, ts, samples, rate, peak (an array of per-channel dBFS).
scte t_us, tc, rail, valid, ops, absolute, plus insert_type, event_id and pre_roll_ms when a splice decoded.
stats A periodic rollup (~20 Hz): measured_fps, nominal_fps, jitter_mean_ms, jitter_peak_ms, av_sync_ms, dropped_video, dropped_audio, tc_breaks, queue_video, integrated_lufs — the receiver's own view alongside the arrivals you can measure for yourself.
end t_us, video_frames, audio_frames — the writer's own totals, which is how --analyse knows whether the file is whole.

The reader is deliberately tolerant: unknown record types are counted and skipped rather than treated as corruption, unknown fields on a known record are ignored, and a malformed or non-UTF-8 line is counted and excluded rather than aborting the analysis. A newer recorder can therefore add records and fields without breaking an older analyser.

The buffer is flushed on a one-second timer and on close, so a hard kill loses at most a second of tail rather than the whole file.

Making a measurement run

From the GUI, press Measure in the title bar, having first chosen a length in the duration dropdown beside it: 10 s, 30 s (the default), 1 min, 5 min, 15 min or Continuous. The button is always visible, but it is disabled until a source is connected — a recording with no source in it is just a header line — and hovering it while nothing is connected reads Connect to a source first.

A run is a timed measurement, not a tape you have to remember to stop. Choose a length, press once, and the instrument does the rest. While the run is going the title-bar area shows:

  • ■ Stop, which ends the run early;
  • the elapsed time against the total, 0:12 / 0:30;
  • the frame count so far;
  • a progress bar filling toward the chosen duration.

A run ends itself when its time is up, whether or not frames are still arriving. The timer lives in the capture thread and is checked on every loop iteration rather than once per received frame, and that distinction matters in exactly the case you most want to measure: a source that stalls part way through. A timer checked per frame stops being checked at all when the frames stop, and a 30-second run against a source that dies at second 3 would sit open forever and leave a file with no end record on it. As it is, the run closes at second 30 and you get a whole, analysable recording of the stall.

Continuous is the old open-ended behaviour, and it must be stopped by hand. Use it when you are waiting for an intermittent fault whose timing you cannot predict, rather than characterising a source you already have in front of you.

Recordings land in **%USERPROFILE%\Documents\CloudCast Scope\** as scope-<source-slug>-<unix-seconds>.jsonl, so two runs never silently overwrite each other and nothing depends on where the process happened to be started from. If Documents does not exist, or has been redirected somewhere unavailable, the system temp directory is used instead. The directory is created if it is not there yet. While a run is going the full path of the file being written is shown in the left-hand panel, and hovering the progress display shows it too — so there is never a question of where the evidence went.

When the run finishes — by its timer or by Stop — the file is closed and flushed, then analysed automatically, and the Report tab (below) opens with the result. You do not have to go and find the file and feed it to --analyse yourself; that path still works, and the report is the same one, but the ordinary case is now press, wait, read.

If a run cannot be started, or a write fails part way through, the run stops and a red Recording failed message appears in the left-hand panel with the underlying error text (a permission denial, a full disk, a path that cannot be created). A recording that silently stopped is worse than none, so the failure is always on screen rather than only in a log.

From the command line, nothing has changed — --probe with --seconds is the headless equivalent of a timed run, and always was:

cloudcast-scope --probe "Decoder" --seconds 60 --record decoder.jsonl
cloudcast-scope --analyse decoder.jsonl

--record also works on a GUI launch (cloudcast-scope --source "Decoder" --record run.jsonl), in which case recording starts as soon as the connection is up, so the session header names the source actually attached to.

--record takes the path you give it verbatim, relative to the working directory, and creates any missing parent directories, so --record logs\today.jsonl works from a fresh checkout without a mkdir first. The same failure reporting applies on a GUI launch.

The Report tab

The Report tab holds the analysis of the most recent measurement run. Before the first run of a session it reads No measurement run yet.; afterwards the result stays there until the next run replaces it, so you can go back to the scopes, compare against the live picture, and return to the numbers.

The analysis runs on a worker thread, so the tab fills in a moment after the run ends and the rest of the application keeps painting and keeps measuring while it does. That is not a nicety — a 15-minute run at 50 fps is 45 000 video frames, and doing that work on the UI thread would lock the window for as long as it took.

At the top is the headline block: the verdict, coloured — green Well clocked, amber Mostly well clocked, red Bursty — with the deadline-emission percentage beside it, which is the single number the whole section exists to produce (the pacer simulation explains what it means). Under it, the figures worth reading before anything else, with out-of-spec values coloured:

Row What it tells you
Duration How long the run actually covered. Compare it with the duration you asked for.
Frames Video and audio frame counts, named separately — the same two-counters-not-a-ratio warning as §7.
Frame rate Measured against nominal. A measured rate well under nominal is a starved source, not a jitter problem.

Reading a report: a starved source

A real 30-second run against an NDI test-pattern generator that had been left in the background and was emitting roughly one frame a second. The headline block:

Duration          30.0 s
Frames            28 video, 263 audio
Frame rate        1.038 measured / 29.970 nominal
Arrival interval  963.05 ms mean, sd 187.10 ms (560.7% of a frame)
Off-phase cause   752 late, 2 bunched
Dropped           0 video, 0 audio

Read it top to bottom:

  • Dropped 0 video, 0 audio. Nothing was lost. A dropped-frame counter — the check most people reach for first — passes this source cleanly, and that is the entire argument of this section in one line.
  • 1.038 measured / 29.970 nominal. The sender declares 29.97 fps and delivers one frame a second. It is not jittering around the right rate; it is barely sending.
  • 963.05 ms mean, sd 187.10 ms (560.7% of a frame). The standard deviation is five and a half frames. There is no clock here to speak of.
  • 752 late, 2 bunched. Late dominates overwhelmingly, which points at starvation — the source stalling — rather than at batching on the path. Chase the sender, not the NIC.
  • 96.67% deadline emissions, hence Bursty. Almost every frame a downstream pacer emitted would have come from its own timer rather than from an arriving frame.
  • 28 video, 263 audio. Worth noticing on its own: the audio rail is healthy while the video rail is starved. The two fail independently, so a source that is plainly still alive on audio can be delivering nothing usable on video.

This is also what the "connected but no frames arrive" failure in §11 looks like once you measure it instead of watching it: connection up, timecode present, audio flowing, zero drops, and a video feed that is not there.

Reading the analysis report

This is the full text report — what --analyse prints, and what the lower half of the Report tab shows. Six sections. Taking them in order:

Session header. Source, duration, frame counts, and the end record line. If the writer's own totals disagree with the number of records actually read, that line says MISMATCH — recording is truncated or lossy; if the end record is missing entirely it says ABSENT — recording was cut short. Either means treat every count below as a lower bound. format names the raster and the nominal rate and, in brackets, where the rate came from: declared (the sender filled in fps_n/fps_d), inferred from median interval, or assumed. A silently invented period would make the whole pacer section a lie, so it is always stated. The recorded line carries the wall-clock date the recording started, taken from the header's started_utc; recordings written before that field existed show the source and tool version with no date.

Video arrival intervals. Count, mean against nominal, median, min/max, standard deviation as an absolute figure and as a percentage of a frame period, then percentiles. The percentage is the number to read first: an sd of 3 % of a frame is a well-clocked source; 87 % is not.

The Airlock pacer simulation — see below.

Timecode. How many frames carried a non-zero timecode, the mean/median timecode step, and how many steps differ from one frame by more than half a frame. A source with no timecode gets an explicit paragraph saying so rather than a clean-looking zero.

Audio. Frame and sample counts, rate and channel count, how many seconds of samples the file holds, the inter-arrival interval statistics, the worst peak, and counts of frames at or above −0.1 dBFS ("near clip") and at or below −90 dBFS ("silent"). Peaks in a recording are already per-channel dBFS, so this is a cheap summary, not a substitute for the live loudness meter.

Verdict. Plain English, with a stated rule behind it:

Verdict Condition
WELL CLOCKED Deadline emissions below 1 % and sd below 25 % of a frame.
MOSTLY WELL CLOCKED Deadline emissions below 5 %.
BURSTY Anything else.

followed, whenever there were any deadline emissions, by a dominant cause: BUNCHING (bunched more than twice late), LATE FRAMES (late more than twice bunched), or MIXED — each with the specific things to go and look at.

The arrival interval histogram

The shape is the diagnosis, and no summary statistic substitutes for it. Two recordings with an identical mean interval and zero drops can have completely different histograms.

  • A well-clocked source is one tight cluster around the nominal period. The <- nominal marker sits on or beside the tallest bar.
  • A bursty source is bimodal — a spike near zero (frames arriving in clumps) plus a spread of long gaps — and the nominal bin is empty. Seeing the nominal marker point at a bar containing 0.0 % of the intervals is the single clearest signature of the fault.

Mechanics worth knowing when reading one: there are 24 bins; the top of the range is clipped at the 99.5th percentile with the tail collected into a final overflow row (otherwise one 3-second stall flattens the whole distribution into a single bar); and a non-empty bin never renders as blank, because a single stray frame in a long gap is exactly the event being hunted.

The pacer simulation

This is the headline. It replays the recorded arrival times through the rules of a downstream output pacer — a literal transcription of Airlock's OutputPacer, not an approximation, because a metric that is nearly right sends people chasing the wrong fix — and reports what fraction of output frames the pacer would have had to emit from its deadline timer rather than from an arriving input frame.

The model, with the engine's shipping defaults:

  • period = the nominal frame period (40 ms at 25 fps).
  • grace = 0.25 × period. The deadline timer wakes at phase + grace.
  • min spacing = 0.50 × period. An input frame arriving less than this after the last emission is deferred — stashed rather than emitted.
  • On a deadline wake the pacer emits, then advances its phase by whole periods until it is back ahead of now.

Every deadline emission is attributed to one of two causes:

Cause Meaning Usual origin
late The input gap exceeded period + grace, so the pacer reached its deadline with nothing new to send. Starvation: the source is stalling, dropping, or being delivered late. Check sender load, encoder stalls, link loss.
bunched A frame had arrived inside the minimum spacing and been deferred; the timer flushed it. Batching upstream: a sender writing several frames at once, or a network path coalescing them. Check the sender's output scheduling and NIC interrupt moderation / receive coalescing on the path.

deferrals counts input frames stashed rather than emitted; context restates the same thing distribution-side — what share of intervals fell below min spacing and what share exceeded period + grace.

DEADLINE 0.00 % means the pacer stayed input-paced throughout, and whatever complaint you are chasing is not in this feed's arrival timing.

The grace sensitivity table

Under the simulation, the same replay is run with the grace widened to 0.50, 0.75 and 1.00 × period (min spacing held at 0.50). The purpose is to tell two situations apart: if a wider grace collapses the deadline rate, the feed is merely marginal and a configuration change fixes it; if it barely moves, the source itself has to be fixed.

The table is not monotonic, and you must not read it as a tuning curve. Widening the grace can lock the pacer's phase just after each burst and make matters worse before it makes them better. In the bursty example below the rate goes 49.97 % → 49.97 % → 99.87 % → 0.00 % as grace goes 0.25 → 0.50 → 0.75 → 1.00; at 0.50 the deadline count is unchanged but the cause flips almost entirely from bunched to late, and at 0.75 nearly every emission has become a deadline emission because the timer has taken over the phase completely.

Read the table as evidence about the source's arrival pattern, not as a recommended setting. "Grace 1.00 fixes it" is an observation about one specific burst period, not a configuration to deploy.

9. SCTE-104

What is decoded

SCTE-104 splice messages carried in NDI metadata as VANC, per SMPTE ST 2010 — DID 0x41, SDID 0x07. The XML looks like:

<vancData version="1.0"><vancPacket did="65" sdid="7" line="10">BASE64</vancPacket></vancData>

The base64 payload holds the 8-bit user data words only, so there is no 10-bit ANC stack to unwind: decode the base64 and the SCTE-104 message is there. Both decimal (did="65") and hex (did="0x41") attribute forms are accepted, and senders that multiplex several VANC types into one metadata frame (AFD, timecode, captions and SCTE-104) are handled by skipping the packets that do not match. Senders that wrap the ST 291 header into the payload are handled too.

Both SCTE-104 message shapes are decoded:

  • multiple_operation_message (MOM) — begins with the reserved marker 0xFFFF, carries a timestamp structure and a list of operations. Unknown opIDs are skipped by their declared data_length rather than aborting the walk, so a splice sitting behind a vendor-private op is still found.
  • single_operation_message (SOM) — begins with an opID and carries no timestamp structure, so its splice is relative by definition.

SCTE-35 section decoding is also implemented in the same library, for gear that carries sections rather than SCTE-104 operations.

Malformed input never crashes the decoder: every read is bounds-checked and arbitrary bytes yield an explicitly invalid cue. A cue can be invalid and still carry a decoded splice — a truncated op list after a good splice, say — which is why the panel reports the two independently, marking the card malformed while still showing the fields.

The two rails

Cues are decoded on both rails, and each card says which one it arrived on:

  • per-frame — metadata attached to a video frame. The cue is anchored to that frame, and the card shows its frame index and timecode.
  • standalone — the separate NDI metadata rail, for senders that emit cues out of band.

Watching only one rail is a common way to conclude that a source "sends no cues". Scope watches both.

Splice fields

The SCTE tab shows the cue count in the tab label and one card per cue, newest first, up to the most recent 200. Each card carries an OUT (break start), IN (break end) or CANCEL chip, the insert type, the event id, and how long ago it was seen — then the decoded splice_request_data:

Field Wire type Shown as
splice_insert_type 1 byte SpliceStartNormal, SpliceStartImmediate, SpliceEndNormal, SpliceEndImmediate or SpliceCancel. A value of 0 (reserved) or above 5 is rejected — a splice that cannot be named must not be acted on.
splice_event_id 4 bytes id N
unique_program_id 2 bytes Unique program id
pre_roll_time 2 bytes milliseconds
break_duration 2 bytes tenths of a second, displayed as seconds (30.0 s)
avail_num / avails_expected 1 byte each Avail 2 of 4
auto_return 1 byte yes / no

Those two unit choices are the one place in the decode where a misread produces an air-critical error rather than a parse failure — a 10× unit error puts the splice at the wrong instant with no other symptom. So the decoder carries an explicit guard: a pre-roll over 60 seconds or a break duration over an hour is far more likely a unit error than a real cue, and the card shows

Values imply a unit misread — treat this splice instant as unsafe.

Do not air a splice flagged that way without confirming the encoder's units.

Absolute timestamps

A MOM's timestamp structure has a time_type of None, UTC, VITC or GPI. Anything other than None means the splice names an absolute instant rather than one relative to the message's arrival, and the card says so loudly:

ABSOLUTE (Utc) — a delay invalidates this cue

This is the field that matters in a delayed path. A relative cue survives a delay: it still means "splice N milliseconds after this message". An absolute cue does not — it names a wall-clock time, a VITC timecode or a GPI edge that has already passed by the time the delayed programme reaches air. Upstream has to be told to send relative cues, or the splice has to be re-timed downstream.

(An unrecognised time_type invalidates the whole message rather than being ignored, because the timestamp is variable-length: without knowing its size the decoder cannot locate num_ops, and every subsequent field would be read from the wrong offset.)

10. Command reference

The release binary is linked as a Windows GUI application so that double-clicking it does not flash up a console window. It re-attaches to the console that launched it before its first write, so run it from a terminal when you want --list, --probe or --analyse output — launched any other way there is no console for the output to reach.

Flags

Flag Argument Default Effect
--source <NAME> — Launch the GUI and connect to the first discovered source whose name contains NAME (case-insensitive). The fragment waits until discovery resolves it, so starting before the source is up simply attaches when it appears.
--list — — Wait 3 seconds for discovery, print name<TAB>url for every source found, exit. Prints No NDI sources found. if there are none.
--probe <NAME> — Headless. Wait up to 10 seconds for a source matching NAME, connect, measure, print a full report, exit. Fails with a non-zero exit if the source never appears.
--seconds <N> 10 How long --probe measures for. Loudness needs at least a few seconds; integrated loudness and LRA want 30 or more.
--record <FILE> — Write per-frame metadata to FILE as JSON Lines. Combines with --probe or with a GUI launch.
--analyse <FILE> — Read a recording back, print the arrival-timing report (§8), exit. --analyze is accepted too.
-h, --help — — Print the help text and exit.

Flags take the following argument, so quote names containing spaces. With no flags at all, the GUI opens with nothing connected.

Examples

Find out what is on the network:

cloudcast-scope --list

Open the GUI already connected, and start recording immediately:

cloudcast-scope --source "Camera 1"
cloudcast-scope --source "Decoder" --record run.jsonl

Capture evidence of an intermittent fault at 3 am without anyone sitting in front of a screen — this is what --probe exists for:

cloudcast-scope --probe "Studio 2" --seconds 300 --record studio2.jsonl > studio2.txt

--probe prints the same measurements the GUI shows, grouped as format / -- timing -- / -- video -- / -- audio -- / -- scte --, one line per channel for audio (peak, true peak, RMS, DC, plus SILENT and n CLIPS markers). It is plain text and greps cleanly.

Then, back at a desk:

cloudcast-scope --analyse studio2.jsonl

11. Scope on the web

Everything in this manual so far describes the desktop application. The same analysers can also be watched from a browser on your network: the same numbers, the same scopes and meters, the same reports, arranged as dashboards you build by dragging widgets onto a grid.

It is the same program. The browser is not running its own copy of anything — it is watching the sessions this machine is already analysing, so what you see in a browser and what you see on the desktop are the same measurements of the same frames.

Turning it on

Top bar → API. Choose whether it should be reachable by this computer only or by the network, set a port (8760 by default), and turn it on. For network access, tick Require a bearer token — the window will generate one for you, and it is what stops anyone who can reach the machine from watching your plant.

Tick Turn on when CloudCast Scope starts to have it come up with the application.

You can also run the server on its own, without the desktop application:

cloudcast-api --listen 192.168.1.80:8760 --token s3cret

Either way the web UI, the REST API, the OpenAPI document and the MCP endpoint are all served from the same port.

Opening it

Open http://<this machine>:8760/ui/ in a browser. The API window lists the addresses that will work and will copy one for you.

The first time, it asks for a name. It is not a login: with no accounts on a LAN, the name is simply where your dashboards are kept, so your layout follows you between machines and someone else's does not overwrite it. If the server requires a token, the page asks for that too and remembers it in the browser.

Sessions started anywhere appear everywhere. An NDI source you are monitoring on the desktop shows up in the browser's session list; a stream someone starts from a browser appears in the desktop application's session list. Whoever started a session is the only one who can stop it over the API — the desktop can stop anything.

Dashboards and presets

A dashboard is a grid of widgets. Drag one out of the drawer, drop it where you want it, drag its corner to resize. Changes save to the server under your name as you make them.

The preset menu builds a ready-made dashboard for each tab of the desktop application — NDI Scopes, Audio, Timing, SCTE-104, Measurement run and Overview; AoIP, Packets, Clocks and the plant report; every HLS tab; plus SRT capture, where you upload a .pcap and get the same report the command-line tool produces. They are a starting point: rearrange them and they stay rearranged.

Widgets follow the dashboard's chosen session rather than a fixed session id, so a dashboard keeps working after a source is restarted.

The clocks view is the one to reach for when audio is glitching and nobody can say why: the PTP grandmaster's behaviour, the Livewire clock's cadence against an ideal 0.25 ms grid, and every source's media clock measured against the grandmaster.

For HLS, each desktop tab has its dashboard: the findings with their remedies, the segment window, the timeline, the decoded audio, and the SCTE-35 breaks with the reason a consumer fires twice on one break.

An SRT capture is analysed the same way, whether you upload it or point at a file already on the host. Only SRT headers are read, never payload, so an encrypted stream analyses exactly as well as a clear one.

Picture and listen

Two widgets cost real bandwidth, so they are strictly on demand.

Picture shows the video as a JPEG monitor, with its own size and quality controls. Nothing is scaled or encoded until the widget is on screen, and it stops as soon as it scrolls away. At its default 640 px and 10 frames a second it is about 85 KB/s.

Listen plays the audio: the NDI source's first pair, or the AoIP stream the meters are following. Nothing is captured or sent until you press Listen. Audio is sent as plain 16-bit PCM — no codec, so no codec delay — which is about 190 KB/s for a loud stereo 48 kHz stream and far less when it is quiet. Choose a jitter buffer between 40 and 200 ms; 80 ms is a good starting point on a wired network. The widget shows how much audio is buffered, the round trip to the server, and any underruns.

Audio has its own dashboard, with the meters, loudness, phase correlation and spectrum the desktop shows.

A measurement run can be started from the browser as well as the desktop. It records every frame's arrival for the time you choose, then reports how a deadline-paced output would have coped.

Discovery

The Discovery dashboard shows what the network announces about itself over mDNS — NDI sources, Dante and Ravenna devices, NMOS registries — with the host and port each one resolves to, which box announced it, and anything wrong: two devices claiming one name, a host name with two addresses, an instance whose target never announced an address.

Listening is passive and costs the network nothing. Pressing Ask sends a single browse query, which is the only thing here that puts a packet on the wire — and on a quiet VLAN it is usually what turns an empty list into a full one.

Who can reach it

Scope on the web is built for a plant network. There is no TLS and there are no accounts: a bearer token gates access and that is the whole security model. That is a sensible trade on a LAN and a poor one on the open internet.

The server therefore tells you what it is bound to. If it is reachable from the network with no token, or if this machine holds a publicly routable address and the server is bound to all interfaces, it says so on start-up, in the API window, and across the top of the web UI itself. If you need Scope off-site, put it behind a VPN rather than opening the port.

Anyone with the token can use any name, so names are convenience, not security.

What it costs

The server only produces data someone is looking at. A widget that scrolls off screen unsubscribes; a browser tab that is hidden drops every subscription and then the socket. With nothing subscribed, the analysers skip the work altogether — an NDI source costs 1.65 ms a frame with nobody watching the scopes and 2.6 ms with.

Each frame is serialised once and sent to every browser watching it, so more viewers cost far less than you would expect. Measured on the lab machine with the NDI Scopes set (nine topics, 121 KB/s each) on a 960×540p25 source:

Browsers Server CPU for the streaming Per browser

2 7.2% 36 ms/s
5 8.6% 17 ms/s

Ten browsers cost about one and a half times what one costs, not ten times.

The page follows the browser's light or dark setting, and a switch in the top bar overrides it.

The session's own analysis — which happens whether or not anyone is watching — was another 7 to 9% of a core.

12. Troubleshooting

No sources found

The source list stays on Discovering…, or --list prints No NDI sources found.

  1. Is the NDI Runtime installed? If it is not, the application does not start at all — it exits reporting NDI runtime not found and listing every path it tried (§1). A window that opens but finds nothing is a discovery problem, not a runtime problem.
  2. Is anything actually sending? Check with another NDI tool on the same machine. If nothing else can see the source either, the problem is upstream.
  3. Firewall. NDI discovery is mDNS on UDP 5353 plus TCP for the streams themselves. A host firewall that blocks inbound mDNS will show an empty list on a network that is otherwise fine. Scope itself installs no firewall rule and needs none for outbound connections, but the runtime's discovery has to be allowed.
  4. Different subnet. mDNS does not cross a router. Sources on another VLAN will never appear by discovery alone — they need an NDI Discovery Server, or the sender's machine and this one need to share a subnet.
  5. The wrong adapter. A machine with several NICs (a media VLAN, a corporate VLAN, a VPN, WiFi) may be discovering on the wrong one. Configure the NDI runtime's adapter settings through NDI Tools' Access Manager.
  6. Give it a moment. Discovery is continuous but announcement-driven; --list waits 3 seconds, which is usually but not always enough on a busy network. The GUI keeps looking indefinitely.

Not connected or no picture

Three distinct states, and the title-bar dot tells them apart:

  • Dark grey dot, not connected, centre pane reads Select a source. Nothing has been selected. Click a name in the list.
  • *Amber dot, source name shown, centre pane reads Waiting for video….* A receiver exists but no sender is connected to it (Connections on the Timing tab reads 0). The source was advertised but is not delivering — it has gone away since it was announced, is refusing the connection, or is reachable for discovery but not for the stream (a routing or firewall asymmetry).
  • Green dot but still no picture. Check the Picture checkbox in the title bar — the pane reads Picture hidden when it is off. Then check the bandwidth: Audio only delivers no video by design. If neither explains it, the sender may be connected but idle — see below.

A red error line at the bottom of the source panel means the receiver could not be created at all; the message is the runtime's own.

Connected but no frames arrive

A source is listed, the dot is green, Connections reads 1 — and nothing is happening. This is a real and easily-misread state: an NDI sender can advertise itself and accept a connection while delivering no frames at all. The connection indicator says a TCP session exists, not that media is flowing.

The signature on the Timing tab:

  • connections 1 — the sender accepted the connection;
  • measured fps 0.000 — nothing has arrived to time;
  • the video frame count stuck at 1 (or 0) and not moving;
  • jitter mean, peak and standard deviation all exactly zero, because there are no intervals to measure.

This was observed on a live SRT decoder's NDI output whose own input had gone away: the decoder kept its NDI sender up and kept accepting connections while producing nothing.

Trust the frame counters and the measured fps, not the connection dot. A green dot with a frozen frame count is a source that is not sending. Go and check whether the sender actually has an input — a decoder with no stream, a camera on standby, a switcher output not routed — rather than looking for a network fault between it and here, because the network is plainly working: the connection was made.

A near relative of this state is the source that is connected and barely sending — a frame a second against a declared 30 — which looks alive enough to fool a glance at the picture pane. To capture either as evidence rather than an impression, press Measure with a 30 s duration and read the Report tab: the run ends on time even though the frames have stopped, and the headline names the starvation numerically. §8 walks through exactly such a capture.

High dropped audio counts

Remember the units: 0 video, 1214 audio is zero video drops and 1214 audio drops, not "0 of 1214".

Audio dropping while video does not is usually about the monitor, not the source. Capture and analysis run on one thread; video analysis is the expensive part (~5 ms per 1080p UYVY frame, ~8 ms for BGRA, around 21 ms at 2160p), and audio frames are small and frequent, so audio is what the receiver discards when that thread falls behind. Confirm by looking at Queued audio on the Timing tab: a queue that sits deep and a rising drop count are the same story.

What to do:

  • Analysing every frame of a 2160p50 feed is not realistic on one core. Monitor it at Lowest bandwidth if you only need audio and timing — but read §3 first, because that invalidates every video measurement — or use Audio only, which is the honest choice when audio is the subject.
  • Close other work on the machine. This is a measurement tool; giving it a core is reasonable.
  • If the drops matter as evidence about the source, take a measurement run instead (§8) — a 30 s or 1 min run analyses itself into the Report tab and describes the source rather than this monitor's thread budget. The --analyse verdict explicitly notes when the recorder itself logged drops, so some long gaps may be capture-side loss rather than sender behaviour.

Unexpected GAMUT alarms

In rough order of likelihood:

  1. The colour matrix is inferred wrong. Check the title bar. A source at 576 lines or fewer is decoded as BT.601; anything taller as BT.709. A downscaled HD feed at, say, 960×540 that was encoded 709 will be decoded 601 and will flag heavily — tens of percent of the raster (§5).
  2. Bandwidth is set to Lowest. The proxy is a different raster, separately encoded, and at 360 lines it also flips the matrix inference. Two reasons the number is meaningless. Switch to Highest.
  3. The source is genuinely full-range RGB. A BGRA/RGBA graphics source with pure primaries in it is out of the 16…235 box on all three channels by definition — full-range red flags every pixel. That is a correct measurement of an incorrect signal for a studio-range path, and the fix is upstream.
  4. A few hundred pixels on a clean picture. Expected, not a fault: 4:2:2 chroma is shared across pixel pairs, so every hard colour transition produces a handful of genuinely out-of-gamut edge pixels. This is exactly why the alarm threshold is 0.1 % of the raster rather than one pixel.
  5. The signal really is out of gamut. Look at the RGB parade — a genuine fault is visible as a trace pushing past the 16 or 235 graticule on one or more channels, and the vectorscope will show excursions past the target boxes.

Unexpected CLIP alarms

Read §6 Clipping first. The rule is |x| ≥ 1.0, so a genuine 0 dBFS test tone reports clips continuously and the chip stays lit — that is correct behaviour and not a fault. Press Reset stats and watch whether the count climbs again: a static count is history, a climbing count is happening now. On programme material any clip count at all is worth chasing.

Measurements look wrong on Lowest bandwidth

They are wrong, and the amber note under the bandwidth radio buttons says so: Proxy — video measurements are not of the real feed. At Lowest NDI delivers a separately-encoded ~640×360 proxy. Every video measurement — luma statistics, gamut counts, sharpness, black and freeze detection, the letterbox geometry and all four scopes — then describes the proxy. Audio and arrival timing are still valid. Switch to Highest (full analysis) for anything you intend to act on; note that the change reconnects and restarts the cumulative counters.
